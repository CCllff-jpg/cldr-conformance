# 待提交清单：5 条上游 issue

> 照着做就行，每条 1–2 分钟。全部提交约 10 分钟。

## 怎么用（三步，不用命令行）

1. 点开"新建 issue"链接（需要 GitHub 登录）
2. **标题**：从下面每条的「标题」里复制
3. **正文**：打开 `bodies/` 目录下对应的文件 → **全选（Ctrl+A）→ 复制（Ctrl+C）→
   粘到 GitHub 正文框（Ctrl+V）**

`bodies/` 里的文件**已经是纯正文**：开头一句用来说明来由（"我在写一个 CLDR 一致性对拍工具…"），
后面是完整的现象、复现、依据、建议。直接全选复制即可，不需要删任何东西。

（如果你习惯命令行，`upstream-issues/` 下的原文件第一行是标题，从第二行起才是正文。）

## 建议顺序

**02 → 01 → 05 → 03 → 04**
先提最确定、最严重的（溢出、数字系统），再提行为差异（MF2），
最后提两条"想确认"性质的（默认值、双向控制符）——这样即使后面两条没提，前三条也够。

| 正文 | 打开 [`bodies/05-MF2回退.md`](bodies/05-MF2回退.md) → 全选复制 → 粘贴 |

## 对方可能怎么回，怎么答

| 对方说 | 建议回应 |
|---|---|
| **"这是有意设计"** | 说明我们对拍基准是 CLDR 官方测试数据，并问能否在 README/文档里标注这个取舍；我们这边会把这类差异从"缺陷"改标为"默认值差异" |
| **"已修复，试试 x.y.z"** | 升级版本重跑，把新的一致率贴回 issue（这就是最有说服力的前后对比） |
| **"能不能给更多信息"** | 附 `moon run cmd/conform -- --impls <id> --all-samples --format json` 的输出，或直接说是哪个文件哪一行 |
| **"你这是什么工具"** | 给仓库链接 + `moon run cmd/conform -- --impls <id> --format markdown` 的输出，说明它按 CLDR 官方数据对拍 |
| 没有回复 | 不用追。issue 留在那里本身就是贡献，也可以在 README 的"本工具发现的问题"里列出链接 |

## 提完之后可以做的事

把修复后的版本接进来重跑，报告里就有了**前后对比**：

```
moon run cmd/conform -- --impls moonlocale --format markdown
```

如果某个库修了缺陷，一致率会变，这正好证明这个工具是"活的"——
它会随着生态一起变好，而不是一份写完就过期的统计。
